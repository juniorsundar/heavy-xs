# GUI and legacy Lua extension contract inventory

Evidence for [Inventory the GUI and legacy Lua extension contract](../issues/39-inventory-gui-extension-contract.md), supporting [A fast, deeply customisable GUI without breaking Lite XL plugins](../gui-map.md). This is an inventory, not a compatibility policy or redesign proposal.

## Provenance and bounds

- Source revision: `e556d388892280d8343a82a625941137e3a6ac5f` on `rust-port`; inspected 2026-10-23. No changes to `src/`, `data/`, `tests/` or `scripts/` were present during inspection.
- Method: semantic Lua symbol navigation, selective body inspection, source/test-runner audit and cross-checks of representative bundled plugins. The Rust language server was not active; Rust paths were inspected with ordinary file/search tools. No builds, tests, benchmarks, live desktop review or third-party plugin execution were performed.
- **Documented here** means repository comments/annotations describe intended use; it is not a newly approved stability guarantee. **Observed** means current code or a bundled caller relies on the behaviour. **Unestablished** means this inventory has not demonstrated compatibility, not that the behaviour may be dropped.
- The inventory covers the GUI path and representative extension patterns, not every method or every combination of plugins. Existing acceptance expectations remain unchanged. The subsequent compatibility ticket must decide evidence scope without silently excluding undocumented usage.

## 1. Current ownership and startup-to-ready path

| Stage | Current implementation and observable ordering | Evidence |
| --- | --- | --- |
| Bootstrap | Rust creates a Lua state, opens libraries, registers native modules and globals, then runs the bootstrap chunk. It executes `core/start.lua`, requires `LITE_XL_RUNTIME` or normal `core`, calls `init()`, then `run()`. Test runtimes can therefore bypass normal GUI initialisation without substituting the native implementation. | [app bootstrap and module registration](../../../src/app.rs#L18-L75), [Lua-state/restart loop](../../../src/app.rs#L92-L159) |
| Lua environment | `start.lua` establishes version/scale/path globals, user-first Lua/native module search paths, native-plugin loading, relative `require` support and initial helper modules. This snapshot declares mod-version `4.0.0`; historical upstream documentation is not a substitute for that fact. | [environment and search paths](../../../data/core/start.lua#L1-L45), [relative require](../../../data/core/start.lua#L49-L121) |
| Core module load | Requiring normal `core` already loads configuration and the default theme; the theme requires `core.style`, which loads bundled fonts at module scope. Initialisation work therefore begins before `core.init()` and before user/plugin modules run. | [core dependencies](../../../data/core/init.lua#L1-L20), [theme](../../../data/colors/default.lua#L1-L2), [font loads](../../../data/core/style.lua#L37-L43) |
| Normal GUI construction | `core.init()` creates shared state and `RootView`, command/status/nag/title views. It constructs the default split tree **before loading plugins**; a comment explicitly identifies plugins requiring initialised default nodes. Default commands are registered before plugins so plugins can override them. | [normal GUI initialisation](../../../data/core/init.lua#L262-L372) |
| Plugin loading | User/project modules enter the priority list at `-2`/`-1`. Discovery visits data before user directories and keeps the first same-filename entry's metadata, while user-first `require` resolution can load the user copy's code. Thus a bundled copy's version/priority metadata can govern a user replacement. The list sorts by priority, then name. Version/config gates precede synchronous loading; successful loads can invoke configured `onload`. Code run during loading can mutate the existing GUI and registries. | [plugin details/version checks and sorting](../../../data/core/init.lua#L503-L590), [discovery/load/onload](../../../data/core/init.lua#L593-L657), [user-first module paths](../../../data/core/start.lua#L23-L26) |
| Window and documents | After plugin loading, `core.init()` reuses an existing/persisted window or creates one, restores geometry, opens command-line files and configures the title border. A plugin can itself call native functions earlier, so this is normal-path ordering, not a guarantee that no plugin creates a window. | [window/open-document ordering](../../../data/core/init.lua#L370-L426) |
| First visible content | Native creation starts hidden. A redraw traverses Lua views and emits renderer commands; changed cached regions lead to presentation, and the first successful presentation shows the window. Source ordering distinguishes initialisation, first presentation and input readiness; it supplies no measured startup duration. | [Lua frame](../../../data/core/init.lua#L926-L982), [hidden creation/presentation](../../../src/native.rs#L279-L346), [window presentation call](../../../src/renwindow.rs#L231-L236) |

### State shared with plugins

`core.root_view`, `active_view`, `last_active_view`, `docs`, `projects`, `window`, `redraw`, the clip stack and coroutine registry are mutable Lua state rather than an isolated declarative plugin surface. Classes/modules are shared tables obtained through `require`. This is directly visible in [core initialisation](../../../data/core/init.lua#L314-L372), [focus transitions](../../../data/core/init.lua#L682-L699), [thread registration and clipping](../../../data/core/init.lua#L708-L736) and the plugin examples below. It does **not** establish that every field is a promised public interface.

## 2. Input, focus, commands and scheduling

1. Native window callbacks translate OS events to owned records in the Rust queue; producers do not call Lua. `system.poll_event` pumps nonblocking native events when initialised and serialises queue records to the established event names/arguments. `wait_event` reports readiness without consuming the event. Coordinate scaling happens at the native-to-Lua conversion, while `renwindow:get_size()` reports draw-target pixels. See [native callbacks](../../../src/native.rs#L370-L430), [owned queue/coordinates](../../../src/platform.rs#L1-L62), [event packing](../../../src/sysevents.rs#L55-L155), [wait semantics](../../../src/sysevents.rs#L242-L258), [window size/scale](../../../src/renwindow.rs#L199-L215).
2. `core.step()` consumes events before updating. `core.on_event` routes text input to the root/active view; IME editing goes through `core.ime`; keypresses go through keymap unless IME composition suppresses them. Mouse press/wheel handlers get first refusal before key bindings. A handled key command can suppress its accompanying text-input event. Root mouse routing prioritises the context menu, dividers/tabs and mouse grabs before view delivery. These ordering/consumption rules are observable even if function names remain unchanged. See [event dispatch](../../../data/core/init.lua#L857-L911), [step ordering](../../../data/core/init.lua#L926-L961), [root mouse routing](../../../data/core/rootview.lua#L169-L204), [active-view text forwarding](../../../data/core/rootview.lua#L463-L465).
3. Node activation updates local `active_view`, calls `core.set_active_view`, then calls the old view's `on_mouse_left` on a change. Global activation stops IME first, manages text-input eligibility and honours a view's `force_focus` through `next_active_view`. See [node activation](../../../data/core/node.lua#L192-L200), [global focus](../../../data/core/init.lua#L682-L699), [IME stop/location](../../../data/core/ime.lua#L65-L89). These are lifecycle relationships, not just method signatures.
4. `command.add` stores/replaces named handlers and predicates. Class predicates support inheritance, while a module-name predicate ending `!` requires exact identity; predicates can return arguments for handlers. `command.perform` runs through `core.try` and treats an execution error as handled. `keymap.add` prepends new candidates unless overwriting, and key dispatch tries candidates until handled. Function bindings fall through only on explicit `false`; command eligibility is separate. See [command declarations and registration](../../../data/core/command.lua#L5-L93), [command dispatch](../../../data/core/command.lua#L137-L171), [binding insertion](../../../data/core/keymap.lua#L123-L170), [key dispatch](../../../data/core/keymap.lua#L202-L231).
5. `core.run()` resumes Lua coroutines, decides when to step, then waits or sleeps according to focus, blink timing, requested redraws and `config.fps`. `core.step()` updates the root before checking whether a redraw is necessary. Coroutine scheduling is cooperative: the time-budget check occurs **between** resumes and cannot preempt one long-running resume. No hotspot or latency number is established by that structure. See [thread registration](../../../data/core/init.lua#L708-L719), [scheduler](../../../data/core/init.lua#L985-L1021), [run loop](../../../data/core/init.lua#L1024-L1073).
6. Quit/restart removes projects before setting exit flags. `core.step()` explicitly returns before GUI update/draw after those flags, protecting plugins that assume a root project exists. Restart persists the window, creates a new Lua state and invalidates the rendering cache. See [exit/restart](../../../data/core/init.lua#L479-L501), [post-quit guard](../../../data/core/init.lua#L946-L950), [Rust restart](../../../src/app.rs#L143-L159). This is a currently tested compatibility-sensitive ordering, not a hypothetical concern.

## 3. Views, layout and composition

| Module / surface | What is documented or observed |
| --- | --- |
| [Object](../../../data/core/object.lua#L1-L80) | `extend` constructs metatable inheritance, instances call `new`, `is` tests exact class identity and `extends` walks inheritance. Replacing a class table can affect identity-sensitive callers even when methods look identical. |
| [View](../../../data/core/view.lua#L37-L66) | Documented mutable `position`, `size`, `scroll`/`scroll.to`, cursor, scrollbar objects, scale and application/session context. Base methods provide input/scrolling, geometry and empty draw hooks. [Update](../../../data/core/view.lua#L280-L319) detects global scale changes and animates/clamps scrolling. |
| [Node](../../../data/core/node.lua#L14-L28) | Leaves own view arrays and an active view; internal nodes own split children. [Splitting](../../../data/core/node.lua#L81-L116) mutates the existing node into a split and returns a child, with optional locked/resizable dimensions. [Add/remove/close](../../../data/core/node.lua#L118-L200) carries placeholder, focus and callback behaviour. |
| [Layout](../../../data/core/node.lua#L381-L457) | Locked size comes from the active view's mutable size. The binary split calculation assigns geometry to each leaf's active view and accounts for tab space. [Root update](../../../data/core/rootview.lua#L532-L546) updates children **before** recalculating layout. [Node update/draw](../../../data/core/node.lua#L507-L521) updates all tab views, while [drawing](../../../data/core/node.lua#L615-L629) draws only the active view under a clip. |
| [RootView](../../../data/core/rootview.lua#L17-L42) | Owns node tree, mouse/drag/grab state, context menu and deferred-draw queue. [Draw](../../../data/core/rootview.lua#L633-L650) traverses nodes, drains deferred draws, then draws drag overlays/menu and applies the cursor request. `defer_draw` inserts at the queue front and draining removes from the back. Enqueuing after an already-completed drain is not immediate execution. |
| [DocView](../../../data/core/docview.lua#L60-L97) | Holds a document, scroll state and session context; close confirmation depends on dirty state and other references. [Geometry/hit testing](../../../data/core/docview.lua#L129-L243) and [decomposed drawing](../../../data/core/docview.lua#L440-L612) expose line-body/gutter/text/caret/overlay hooks used by bundled plugins; selection highlighting is implemented within the line-body method. Drawing iterates the visible lines rather than the entire document. |
| [CommandView](../../../data/core/commandview.lua#L191-L262) | A document-view-based prompt with submit/suggest/cancel/validate callbacks and focus restoration. Submission validates, exits, then invokes the submit callback. The implementation deliberately still supports deprecated positional `enter` usage and previously set text; a warning is not removal. |
| [StatusView](../../../data/core/statusview.lua#L403-L490) | A named-item interface supplements method overriding: `add_item` rejects duplicate names, constructs/returns an item and supports ordering/removal. This illustrates existing structured extension surfaces alongside open table mutation. |
| [NagView](../../../data/core/nagview.lua#L275-L309) | Queued prompts with selection callbacks and focus-related behaviour. [ContextMenu](../../../data/core/contextmenu.lua#L177-L183) dispatches item commands/functions with supplied arguments. They are Lua GUI behaviour, distinct from native file-dialog transport. |
| [TitleView](../../../data/core/titleview.lua#L38-L66) | Supplies window-title controls and border hit-test configuration. [Scrollbar](../../../data/core/scrollbar.lua) supplies geometry/input/animation/drawing used by views. [EmptyView](../../../data/core/emptyview.lua) and [LogView](../../../data/core/logview.lua) provide placeholder and log UI. These paths were located; their full behavioural combinations were not exhaustively audited. |

## 4. Drawing, caching and presentation are separate costs

- Lua constructs the frame by invoking `RootView:draw` and child drawing hooks. Calls cross the `renderer` interface for rectangles, text and clip commands. `begin_frame` selects a target; `end_frame` processes the cache and releases per-frame font references. See [renderer entry points](../../../src/renderer_api.rs#L519-L605) and [Lua clipping/frame](../../../data/core/init.lua#L721-L736).
- The Rust cache records commands, hashes their covered cells, compares previous-frame hashes, merges changed regions and replays commands into those regions of the retained draw target. With no changed region, it does not call the window presentation path. Command/text vector allocations are retained for the next frame. See [cache frame processing](../../../src/rencache.rs#L298-L400).
- When presenting, the native layer converts/copies **all visible pixels** into the acquired presentation buffer, respecting its rows; it does not send only the cache's dirty rectangles. The draw target and presentation buffer therefore have different retention/copy roles. See [window update](../../../src/renwindow.rs#L220-L247), [presentation copy](../../../src/native.rs#L279-L303), and [existing terminology](../../../GLOSSARY.md).
- Consequently, dirty raster regions do not by themselves establish cheap Lua traversal, command generation, hashing, presentation or startup. This is a distinction between operations in the code, not evidence that any one dominates runtime. There are no new performance budgets or renderer choices in this inventory.

## 5. Concrete bundled extension patterns

These are actual callers, not promises about every third-party plugin. Capturing a method and replacing it composes according to load/require order and the wrapper's delegation; there is no general isolation guarantee.

| Example | Observed dependency |
| --- | --- |
| [TreeView installation](../../../data/plugins/treeview.lua#L525-L552) | Subclasses `View`, obtains the active node and inserts itself with `split("left", view, {x=true}, true)`. It explicitly instantiates the toolbar inside its own node, rather than relying on independent self-installation. It also [wraps project removal/quit and polls watches](../../../data/plugins/treeview.lua#L555-L577). |
| [ToolbarView](../../../data/plugins/toolbarview.lua#L9-L38) | Returned reusable subclass rather than independent node installation. Its [command-driven drawing/input](../../../data/plugins/toolbarview.lua#L57-L102) uses command validity and restores the previous active view before dispatching an action. |
| [Autocomplete](../../../data/plugins/autocomplete.lua#L714-L765) | Captures and replaces `RootView.on_text_input`, `update` and `draw`, plus `Doc.remove`. The old handler runs before its extra work. The drawing wrapper calls the old draw and then queues a deferred callback: the relative drain/enqueue ordering is visible in source; actual popup timing was not measured here. |
| [Draw whitespace](../../../data/plugins/drawwhitespace.lua#L149-L205) | Wraps highlighter notifications and `DocView.draw_line_text`. The draw wrapper explicitly requires exact `DocView` identity when enabled and [delegates after drawing marks](../../../data/plugins/drawwhitespace.lua#L298-L360). Inheritance support cannot be inferred solely from matching method names. |
| [Autoreload](../../../data/plugins/autoreload.lua#L67-L137) | Wraps both global and node-local activation, watches document visibility and uses nag callbacks. Its node wrapper performs visibility work before and after delegation; `Doc.load/save` wrappers retain a result while updating metadata. |
| [Scale](../../../data/plugins/scale.lua#L11-L78) | Mutates global `SCALE`, selected shared style dimensions/font sizes, scroll positions and redraw state. [Configuration and menu integration](../../../data/plugins/scale.lua#L145-L193) changes wheel bindings and wraps the document context-menu method. |
| [Line guide](../../../data/plugins/lineguide.lua#L86-L133) | Captures `DocView.draw_overlay` and extends document drawing, illustrating another independent wrapper on a drawing stage. |

### Configuration and reload boundaries

- [Style](../../../data/core/style.lua#L1-L53) is a shared table of dimensions, padding, renderer font objects and syntax colours/fonts; it is not only a colour theme. Its comments explicitly describe per-token font overrides. Runtime geometry and drawing depend on these values.
- [Plugin configuration](../../../data/core/config.lua#L269-L319) is a metatable registry that lazily creates configuration, merges assigned tables and represents disabled plugins as `false`. It explicitly discourages raw operations and warns instead of unloading an already-loaded plugin when disabled.
- [Module reload](../../../data/core/init.lua#L660-L668) clears `package.loaded`, requires the module and, for an old table, copies new keys back into that old table. It does not remove missing keys, undo installed wrappers, unregister commands or rebuild existing instances. This is not evidence of a general safe hot-reload transaction. No improved reload model is chosen here.

### Evidence gaps for the compatibility decision

The audited assertions do not establish the following; this does not imply the behaviours are absent from runtime execution:

- A plugin-created `View` inserted into the normal node tree, with geometry, clipping, update/draw and close/focus lifetimes asserted.
- Composition/order of independent wrappers on the same method, exact-class versus subclass behaviour, and active/global view identity.
- Default-command replacement, predicate argument forwarding, key binding precedence, event consumption and text/IME interaction through the normal GUI path.
- Default composed appearance and document geometry/hit testing/caret/selection under styles, scaling and font changes; native font or hash tests cover only portions of that chain.
- Structured item/menu/prompt extension, including callback order and focus restoration, and legacy/deprecated call forms still supported by source.
- A bounded external-plugin sample, its installation/version configuration, or compatibility under multiple interacting UI plugins.
- Measured startup-to-ready, visible input latency, customised workloads, idle CPU/memory retention, Lua edit-to-result behaviour or Rust build time/disk cost.

The existing shutdown check is meaningful but narrow; it does not fill these gaps. Additional evidence belongs in the compatibility/acceptance decisions, without weakening any current case or golden.

## 7. Candidate ecosystem sources and reference hazards

No external repositories were fetched or plugins installed for this ticket. Locally documented candidates are:

- [README plugin links](../../../README.md#L20-L23): `https://github.com/lite-xl/lite-xl-plugins`, with `https://github.com/rxi/lite-plugins` also linked at the end of the README.
- [CONTRIBUTING](../../../CONTRIBUTING.md#L7-L16) describes a 3.0 transition and cautions that only core plugins were considered ported in its dated account; [its non-core contribution link](../../../CONTRIBUTING.md#L56-L61) points to `https://github.com/adamharrison/lite-xl-plugins/tree/3.0`.
- [The startup regression comment](../../../scripts/rust-port/startup-check.sh#L108-L110) names `lintplus` and `lsp` as examples motivating the project-lifetime guard. That is a useful lead, not execution evidence for those plugins in this checkout.

A future sample needs pinned revisions, explicit supported version/configuration, representative extension patterns and observed outcomes. The snapshot's mod-version 4 declaration, dated 3.0 contribution guidance and older upstream plugin branches must not be conflated. This inventory does not choose the authoritative compatibility reference or the sample: those questions already belong to [Define the GUI compatibility evidence and extension envelope](../issues/41-define-gui-compatibility-envelope.md).

## 8. Facts now available to the frontier

The current editor already combines structured extension surfaces with broad Lua mutability: status items/commands/configuration coexist with view subclasses, direct node manipulation and captured-method wrappers. A redesign that preserves only native functions would miss behaviours exercised by bundled Lua callers. Conversely, the presence of mutable internals does not tell us which new interfaces should be exposed or promise that arbitrary combinations already work.

The inventory supplies the compatibility discussion and [Establish GUI runtime and customisation iteration baselines](../issues/42-baseline-gui-and-development-costs.md). No compatibility exclusions, architectural choice, measured bottleneck or numerical performance criteria are resolved here.
