# Process-signal quit reference facts

Supports [Choose process-signal quit and wake integration](../issues/37-choose-process-signal-quit-integration.md). Decisions live in that ticket; this is source/document evidence, not a compiled or live result.

## Existing behavior

The exact linked-baseline tag [SDL release-3.4.14 quit implementation](https://github.com/libsdl-org/SDL/blob/release-3.4.14/src/events/SDL_quit.c) installs SIGINT/SIGTERM handlers only over SIG_DFL, preserving SIG_IGN/custom handlers. Its handler sets one pending boolean, later translated by the pump into SDL_EVENT_QUIT; repeated signals can coalesce. There is no second-Ctrl-C force-exit counter. SDL_HINT_NO_SIGNAL_HANDLERS skips installation. Teardown restores default only when SDL's own handler is still installed. The inspected [3.4.18 implementation](https://github.com/libsdl-org/SDL/blob/release-3.4.18/src/events/SDL_quit.c) agrees, but the binding crate's version alone does not establish the linked runtime's behavior.

[Application startup](../../../src/app.rs) ignores SIGPIPE, initializes SDL events before Lua, and keeps that subsystem outside the Lua-restart loop. [Event conversion](../../../src/sysevents.rs) turns SDL_EVENT_QUIT into the existing `quit` tuple. [The Lua consumer](../../../data/core/init.lua) uses core.quit/core.exit and checks quit/restart before further updates/draws; unsaved-document decisions are not replaced by OS termination. A pending process signal is not intrinsically a dialog completion or a Lua-generation-owned result.

[The startup script](../../../scripts/rust-port/startup-check.sh) sends real SIGINT after its ready marker and checks clean exit within five seconds and no update/draw after project removal. It does not test SIGTERM or registration/restart races. Its launcher resets background-job SIGINT disposition so the test is not accidentally exercising inherited SIG_IGN. A caught custom handler does not survive exec like an ignored disposition; custom-handler tests must establish it inside the subject before initialization. See [execve signal inheritance](https://man7.org/linux/man-pages/man2/execve.2.html).

## Tokio and winit

[Tokio 1.53.3 Signal](https://docs.rs/tokio/1.53.3/tokio/signal/unix/struct.Signal.html) documents process-wide handler capture even after a stream is dropped, and coalescing rather than delivery counts. [Its Unix implementation](https://docs.rs/tokio/1.53.3/src/tokio/signal/unix.rs.html) records an atomic pending event and writes to a pipe/socket from the handler; normal runtime dispatch notifies streams. Signal support needs the signal feature, its Unix signal-hook-registry dependency and a live IO-enabled runtime. It does not itself promise SDL's default-disposition-only ownership policy. Prior-disposition checks therefore remain application initialization work, not an assumption about dropping/listening to streams. [signal-hook-registry chaining](https://docs.rs/signal-hook-registry/1.4.8/signal_hook_registry/fn.register.html) can invoke an already-installed custom handler, making dual SDL/Tokio registration a duplication risk.

[winit 0.30.13 EventLoopProxy](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoopProxy.html) wakes the loop from another normal thread. Send/Sync is not a claim of asynchronous-signal safety; never infer handler-safe allocation, locking, Lua or proxy work.

[winit's public AsFd implementation](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event_loop.rs) explicitly supports registering the loop descriptor with an external loop and pumping it. Thus “winit has no descriptor” is incorrect. However its [Wayland keyboard implementation](https://github.com/rust-windowing/winit/blob/v0.30.13/src/platform_impl/linux/wayland/seat/keyboard/mod.rs) uses a calloop timer for repeat. Inspected calloop 0.13.0 `src/sys.rs::Poll::poll` computes waits from an internal TimerWheel. Bare descriptor readability is not evidence that an external wait has preserved those deadlines. A descriptor-only replacement needs further timer integration evidence; no such replacement was compiled or tested here. Winit may itself create helper threads, so avoiding an application signal-reader thread does not establish a thread-free backend.

## Interruption and evidence limits

Linux [signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html) and [poll(2)](https://man7.org/linux/man-pages/man2/poll.2.html) state that multiplexing waits, including poll/epoll_wait, are not automatically restarted by SA_RESTART. Inspected calloop 0.13.0 `src/loop_logic.rs::dispatch_events` retries Interrupted; polling 3.11.0 `src/lib.rs::Poller::wait_impl` retries it against its deadline. Do not infer that every signal destroys winit merely from its outer dispatch-error branch, or claim SA_RESTART alone solves wake-ups. The integrated wait/race behavior still requires real tests.

Only repository/cached-library source and primary documentation were inspected. No handler was installed, runtime built, signal sent, process killed, GUI/bus touched or test run. Tokio/winit remain selected planning references, not editor dependencies adopted by this note. Early-runtime costs, graceful native wakes and listener/final-exit races remain unmeasured/unverified; existing desktop dispositions and acceptance gates are unchanged.
